## 项目现状

- Resonance 是面向 Android 和 Windows 的本地音乐库/播放器，界面以 Kotlin Multiplatform + Compose Multiplatform 实现。
- 共用入口在 `composeApp/src/commonMain/kotlin/com/resonance/player/ui/LibraryShell.kt`；播放器在 `NowPlayingOverlay.kt`；颜色、排版和玻璃表面 modifier 在 `design/ResonanceTheme.kt`。
- 已有深色/浅色/跟随系统三种主题，以及紧凑、中等、展开三种宽度布局。
- 当前视觉方向是深色音乐空间、珊瑚强调色、专辑封面与氛围光；建议保留品牌识别，把层级、日常可读性和工具效率放在装饰效果之前。

## 发现与建议

### P0：先确立一份有效的原生设计规范

**源码可确认。** 仓库内的指导不一致：

- `docs/DESIGN.md` 主张安静的深色唱片空间、珊瑚强调色、避免通用卡片网格，并规定 8dp 间距节奏与 48dp 点击目标。
- `docs/UI-REFACTOR-2026.md` 更强调多层玻璃、发光边框与果冻弹性动效。
- `design-system/resonance/MASTER.md` 则是网页/CSS 规范，使用靛蓝与绿色、Righteous/Poppins 字体、CSS/GSAP/浏览器断点；它不适用于当前原生 Compose 实现，且与其余文档冲突。
- 代码中的实际暗色背景为 `#0C0D14`、玻璃面板为多级透明紫蓝色，与 `docs/DESIGN.md` 的 `#0D1117` / `#151B23` 有差异。

**建议。** GPT 实施前先明确文档优先级，并把 `design-system/resonance/MASTER.md` 标为旧网页参考或改成原生 Compose 规范。统一颜色、表面层级、间距、圆角、排版和动效时长，避免实现时同时追逐互相矛盾的方向。推荐保留深色 + 珊瑚的识别度，减少玻璃边框、发光和阴影的普遍使用，让封面和当前播放状态承担主要视觉表达。

### P1：减少主界面视觉噪声，稳定曲库信息层级

**源码可确认，视觉效果待截图确认。** `LibraryShell.kt` 在一个约 3,000 行的文件中同时承载导航、曲库、搜索、专辑/歌手详情、导入、同步、设置、迷你播放器和多个操作状态。`LibraryShell` 本身接收大量状态与回调，页面改版容易牵连行为，也难以单独检查各状态。

**建议。** 先把设计 token 和共享 UI 元件归一，再按实际页面职责整理可组合页面（例如曲库、播放器、导入/同步、设置）。让 `App.kt` / 现有状态所有者继续负责业务状态，提取 UI 时保留播放队列、歌单持久化、扫描/转换、同步、歌词等现有行为；不要为了外观重写平台服务或数据流程。

曲库建议明确一个主任务（浏览/播放本地音乐），再按重要性安排搜索、多选、缺失元数据补全、专辑/歌手/歌单筛选与批量操作。可通过排版、留白和轻分隔线区分曲目行与内容分组，避免给每项都加卡片、玻璃描边和重阴影。具体行高、封面尺寸和宽屏密度应通过截图检查后再定。

### P1：统一“发现”与曲库搜索的入口语义

**源码可确认。** `DiscoverScreen` 初始状态显示“搜索你的音乐库”，输入后对本地歌曲执行歌名/歌手/专辑匹配；它当前不是在线发现或推荐页。同时，`LibraryScreen` 也有自己的搜索状态与结果列表。

**建议。** 选择并实现一种清晰的信息架构：将“发现”明确命名为“搜索”，并与曲库搜索合并/共享搜索体验；或让它承担真正不同的任务，但不要让两个入口看起来功能重复。按现有产品的本地优先定位，搜索本机音乐应明确写在页面文案中。检查空查询、无匹配、输入中、返回和播放结果等状态。

### P1：核对宽度断点及中等窗口布局

**源码可确认，屏幕效果待运行时确认。** `LibraryShell.kt` 根据宽度使用 `<720dp` 紧凑布局、`720–1099dp` 导航 rail 布局、`>=1100dp` 固定桌面侧栏。桌面窗口最小尺寸为 920 × 640 个 AWT 尺寸单位；代码断点使用 dp，Windows DPI 缩放会影响所属区间，所以需按实际缩放截图确认。此范围目前是侧边 rail + 单一内容区。`docs/DESIGN.md` 对中等窗口提出“有用时使用双栏曲库”，实际是否更好需要结合列表和详情体验验证。

**建议。** 验证 Android 窄屏、横屏/平板、Windows 920dp 最小宽度与 1100dp 以上宽度。特别检查曲目标题与操作是否挤压、详情返回是否直观、导航与迷你播放器是否争夺空间，以及现有列表状态在窗口尺寸变化时能否保留。只有在曲库详情确实需要并有足够空间时才增加双栏，不要仅为满足规范而机械分栏。

### P1：整理播放页的控件优先级与持续动效

**源码可确认，帧率/耗电待运行时确认。** `NowPlayingOverlay.kt` 同时提供封面、同步歌词预览、歌词/队列面板、进度、播放控制、音量和倍速；桌面与紧凑模式使用不同排列。`FluidAmbientCanvas.kt` 使用三个无限重复动画画氛围背景，即使暂停也继续缓慢变化；全局曲库外壳也放置了该 Canvas。项目设计说明要求尊重 reduced motion，但代码未见对应的动效偏好开关。

**建议。** 让封面、歌名/歌手、进度和播放/上一首/下一首成为稳定主层级；随机、循环、音量、倍速、睡眠定时器等次级操作保持容易找到但视觉较轻。减少高亮控件、发光和同时变化的区域。为流体背景提供静态或明显减弱版本，暂停、应用后台或用户关闭动效时停止连续动画；保留必要的状态反馈与歌词跟随动画。对不同尺寸播放页及歌词/队列状态做实际截图验证。

### P1：修复浅色主题主按钮对比度

**源码可确认并按 WCAG 相对亮度公式计算。** `ResonanceTheme.kt` 的浅色主题将 `primary` 设为珊瑚色 `#FF5238`、`onPrimary` 设为白色；两者对比度约为 **3.22:1**。普通按钮文字的 WCAG AA 目标为 4.5:1，因此浅色模式中的主按钮白字可能不够清晰。暗色主题使用的前景色不同，不受这条计算结果影响。

**建议。** 在不丢失珊瑚品牌色的前提下，为浅色主题选取能达到 4.5:1 的前景色/珊瑚色组合，或调整按钮文字样式与表面颜色；同时检查禁用、焦点、选中和辅助文字状态。为常用文本和状态色核对对比度，不仅看深色模式。

### P2：移除机器专属的歌词目录默认值

**源码可确认。** `SettingsScreen` 在尚未保存用户自定义目录时，将 `lyricsFolder` 初始化为 `D:\\Music\\Kugou\\Leonard\\Lyrics`。这是特定 Windows 用户目录，不适用于其他 Windows 用户，也不适用于 Android。

**建议。** 初始状态使用平台服务返回的真实默认值或显示“未设置/使用默认位置”；用平台文件选择器选择目录。跨平台共用 UI 不应展示作者机器的路径作为用户默认配置。

### P2：验证无障碍与文字缩放

**部分可由源码提示，需运行时检查。** 设计规范要求 icon-only 控件有语义标签/tooltip 和至少 48dp 触控区域。当前 UI 有自定义小尺寸 IconButton/TextButton，也有 `contentDescription = null` 的图标（其中不少可能只是装饰）。应在语义树和真实设备上分辨装饰图标与交互控件，并检查长歌名、长歌单名、长路径、系统字体放大、键盘焦点和色弱可辨状态。

**建议。** 对所有只有图标的操作补齐语义名称及桌面 tooltip；保证每个可交互目标达到至少 48dp 或提供等效的可访问触控边界。验证文字自然换行而非被固定宽度裁切，选中状态不要只依赖颜色。

## 建议的实施顺序

1. 明确并修订原生设计规范，冻结视觉方向和 token。
2. 检查当前应用的紧凑、中等和展开截图，记录布局与对比度问题。
3. 整理共享控件和页面职责，不改变领域行为。
4. 优化曲库/搜索信息架构、行列表、空状态及详情状态。
5. 优化播放页层级、浅色主题、设置目录默认值、动效和可访问性。
6. 编译并检查 Android 与 Windows 主要宽度及状态截图；以真实画面为准收尾。

## 建议的视觉检查矩阵

| 平台/尺寸 | 主要场景 |
| --- | --- |
| Android 紧凑竖屏 | 空曲库、曲目列表、搜索无结果、歌单详情、迷你播放器、全屏播放器 |
| Android 横屏/平板 | 曲库列表、详情、全屏歌词与队列、导入/设置页 |
| Windows 920×640 最小窗口 | 导航 rail、曲库搜索和列表、歌词/队列、设置页横向输入框 |
| Windows ≥1100dp 宽度 | 固定侧栏、曲库/详情密度、迷你播放器、导入与同步页 |
| 深色/浅色主题 | 主按钮文字、次要文字、分隔线、选中/禁用/焦点状态 |
| 操作状态 | 扫描中、转换中、失败/成功信息、QR 显示、空列表与长文件路径 |
