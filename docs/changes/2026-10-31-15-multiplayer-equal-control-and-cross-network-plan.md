- 类型：需求澄清 / 协议与验收规划；尚未实现新多人协议
- 适用版本：0.6.5 / 39，不自动升版
- 影响平台：Android、Windows、可选独立网络服务
- 关联：[既有双人协议](2026-10-30-02-listen-together-session-and-native-playback.md)、[聊天与本机记录](2026-10-31-02-encrypted-local-chat-and-device-pairing.md)、[可选伙伴寻址](2026-10-31-04-opt-in-signed-partner-rendezvous.md)

## 需求或问题

维护者实际使用时，手机使用移动数据、电脑使用家里宽带无法连接；手机加入同一 Wi-Fi 后可以连接，播放偶尔卡顿。维护者希望多人一起听，所有人播放控制权平等，收到聊天消息时有提醒，并授权继续检查同一体验中的其他问题。随后明确同意优先直连、必要时使用可选加密中继；服务需要用户自行部署或选择，不暗中部署公共服务。

## 原因与依据

当前 [JvmListenTogetherService](../../composeApp/src/jvmMain/kotlin/com/resonance/player/together/JvmListenTogetherService.kt) 的房间服务器对外监听本机地址，邀请包含候选地址与一个端口；客端直接连接。移动网和家庭路由可能受到 NAT、防火墙与运营商策略限制，地址可发现也不等于入站可达。当前没有 ICE、打洞或内容中继；既有仅登记地址的可选寻址服务不能保证跨网成功。这里的网络原因是根据实现和现象作出的推断，尚未拿到这次手机与电脑的具体链路诊断。

协议依据：[RFC 8445 ICE](https://www.rfc-editor.org/rfc/rfc8445.html)、[RFC 8656 TURN](https://www.rfc-editor.org/rfc/rfc8656.html)；Android 13 及以上的提醒权限见 [Android 官方说明](https://developer.android.com/develop/ui/compose/notifications/notification-permission)。这些标准说明可行机制，不代表当前项目已实现或依赖已选定。

同一服务只有一个 `peer`、一个 `activeWire` 与 `busy` 占用标志；`TogetherCompanionSession` 也只跟踪一个通道/对方。当前客端播放操作进入请求队列，房主通过 `resolveRequest` 才执行。因此仅删除界面上的“批准”不能实现真正多人平权，需升级成员、同步、聊天和故障恢复协议。

## 计划修改与约束

| 方向 | 具体设计与验收要求 |
| --- | --- |
| 连接 | 明确分离信令、候选地址探测、直连与可选中继；评估标准 ICE/STUN/TURN 可维护实现及双端依赖，先并行探测可用直连再回退用户配置的中继；不要把仅交换地址冒充打洞成功。展示连接阶段、直连/中继、失败原因、重试和流量成本。 |
| 隐私与部署 | 音频、聊天、控制和身份认证保持端到端保护；中继只转发密文但可见必要的地址、时长和流量元数据。中继的授权、额度、有效期、抗滥用和密钥配置必须可控；不把密钥放邀请明文或日志，不暗中启用公网服务。 |
| 多人平权 | 改为可扩展成员集合、每成员认证和独立连接状态，所有成员可播放、暂停、切歌和调整共享队列，无房主审批特权。协调节点只负责排序/转发，不能赋予使用者额外操作权；并发命令有确定排序，协调节点离开时明确恢复/重选行为。 |
| 人数与兼容 | 先定义有限且可测的多人房间上限、资源预算与加入时反馈，覆盖至少三台真实原生客户端；不能用理论无限人数或仅双端测试冒充多人支持。协议显式版本协商，旧客户端不静默误入不兼容房间；保留现有聊天数据。 |
| 卡顿 | 采集连接、下载/校验、解码准备、缓冲、漂移、丢包/重连等不含歌曲和聊天内容的本地指标；分别优化网络传输与播放，不把卡顿一概归因于网络。分块校验与可播放缓冲需兼顾完整性、不同编码和 seek，不能绕过已有最终校验。 |
| 消息提醒 | 对真正新收到并持久化的消息发一次提醒，重复投递/重连补发不重复提醒；Android 在用户授权通知且进程仍能收消息时发系统通知，Windows 使用系统托盘通知，默认隐藏消息正文以保护隐私。前台、后台、关闭进程与通知权限拒绝分别测试并说明限制；不承诺离线推送。 |
| 伙伴与数据 | 群聊和多成员下收件人/房间身份绑定、去重、各自清空、已读/送达语义、配对与隐私设置需重新明确；不得删除旧聊天或误发到另一个房间。 |

## 实施顺序

同日续作：已编写消息系统通知、双人控制免审批、稳定连接后重置重试及可选双层 TLS 中继，均按维护者要求未构建测试；多人状态和签名封套仅为未接线基础。以 [通知](2026-10-31-17-chat-notifications-on-android-and-windows.md)、[控制](2026-10-31-18-equal-two-person-playback-controls.md)、[中继](2026-10-31-20-opt-in-encrypted-relay-transport.md)和[多人基础](2026-10-31-21-multimember-room-state-foundation.md)为准，不代表新需求已完成。

1. 先以现有版本建立诊断与多人协议边界，收集用户手机流量/家庭宽带的真实连接结果；保持当前已发软件可用。
2. 分别补齐消息提醒及测试、可选直连/中继的基础能力与可自托管配置，再开发多成员协议、平等控制和队列同步；每个独立功能单独留变更记录。
3. 在无真实凭据/用户歌曲的独立测试环境覆盖直连、禁止直连时走中继、中继失效、断网重连、成员离开、三端以上并发控制、重复消息、权限拒绝和卡顿恢复；必要时单独进行真实移动网络及真实设备验收。
4. 完成后重新构建、验签与实际哈希，按维护者先前授权只发到自己的微信文件传输助手；新宣传片需反映最终真实产品行为。
