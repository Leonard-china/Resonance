# 2026-10-31 — 编写多人房间的平等控制与共享队列状态基础

- 修改日期：2026-10-31（Asia/Shanghai）
- 类型：多人协议基础；尚未接入实际房间
- 适用版本：0.6.5 / 39，未升版
- 影响平台：Android、Windows 共用 JVM 实现
- 关联：[多人与跨网需求](2026-10-31-15-multiplayer-equal-control-and-cross-network-plan.md)、[双人免审批增量](2026-10-31-18-equal-two-person-playback-controls.md)

## 需求或问题

维护者希望多于两人一起听，并且所有成员有相同的播放与队列操作权。现有 `JvmListenTogetherService`、聊天会话与恢复凭据都只对应一个对端，直接移除占用锁会覆盖连接并有消息串发风险。

## 原因与依据

多人房间需要独立成员集合、共享队列、统一排序、离开/重连和重放处理；它还必须把每个操作绑定到已经验证的真实设备身份。当前先实现不涉及传输与密钥的新状态机，不开放未经设计的多对端连接。

## 具体修改

| 文件 | 符号 | 修改 |

| [TogetherGroupCoordinator.kt](../../composeApp/src/jvmMain/kotlin/com/resonance/player/together/TogetherGroupCoordinator.kt) | 成员、队列、快照和 `Action` | 内存状态机提供播放、暂停、前后切歌、进度、选歌和追加/删除/移动队列；所有已接纳成员使用相同规则，允许每位成员贡献由其提供的条目 |
| 同上 | `admitVerified`、`submitVerified` | 有界成员/队列/历史身份数量，按成员递增序号拒绝重复和缺序操作，统一递增房间修订；离房后保留序号底线防止重放 |
| 同上 | 输入校验 | 成员用设备指纹格式，曲目用不透明 UUID，限制标题、歌手和时长；不承载用户本地路径、消息正文或密钥 |
| [TogetherGroupEnvelope.kt](../../composeApp/src/jvmMain/kotlin/com/resonance/player/together/TogetherGroupEnvelope.kt) | `sign`、`verify` | 编写未来群控制/消息的 P-256 签名封套：绑定房间、成员公钥指纹、世代、序号、类型和有界载荷，复制输入以避免验证后数据被外部修改；尚未接入传输或存储 |

## 修改前后行为

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 三位以上成员的内存模型 | 只有单个 `peer` | 已编写可容纳 3–16 位成员的独立状态基础，默认 8 位 |
| 成员执行共享控制 | 旧双人协议依赖单创建端 | 状态机对所有已接纳成员使用同样的命令校验 |
| 重放已执行操作 | 尚无多人序号模型 | 相同或更旧序号被识别为重复，不再执行 |

## 平台与数据影响

新增类尚未被房间服务、界面或中继调用，不改变现有用户的数据、权限或网络行为；默认 8 人、最多 16 人只是内存模型的边界，不是已交付的房间人数承诺。状态仅保存在内存；协调进程退出后没有恢复或重选。

## 验证

依维护者本轮要求只写代码，**未构建、未执行测试或多端验收**。签名封套未做密码学审计，签名不提供消息加密或群成员授权；状态机本身不验证 TLS 设备身份、不处理加入同意、不加密/转发群消息、不维护多对端连接，也没有进行并发或对抗安全验证。

## 限制与后续

继续设计并接入每成员认证、邀请同意、群消息签名/身份绑定、组内加密、断线恢复与协调节点迁移；保证其他成员无法伪造发送方或把私聊错发到群聊。至少在三台真实原生客户端验证统一队列、并发命令、成员加入/退出和弱网恢复之前，不能向用户宣称多人房间已经可用。
