# 2026-10-31 — 先完成旧连接清理再接纳重连

- 修改日期：2026-10-31（Asia/Shanghai）
- 类型：并发问题修复
- 适用版本：0.6.5 / 39；未升版
- 影响平台：Android 和 Windows 共用 JVM 房间实现
- 关联：[稳定连接后的重试](2026-10-31-19-retry-budget-per-stable-connection.md)、[可选中继](2026-10-31-20-opt-in-encrypted-relay-transport.md)

## 需求或问题

长时间一起听时，短暂断网后朋友应能重连，旧连接的收尾不应覆盖新连接。维护者还反馈偶发卡顿；尚未确定该竞态是否是实际卡顿原因。

## 原因与依据

静态阅读 `JvmListenTogetherService` 的房主连接收尾发现，旧实现先释放 `busy` 占用，再清空旧连接、设置恢复期限并更新“已断开”状态。新连接可能在这些步骤之间取得占用并成功进入，随后被旧协程的状态更新覆盖。另外，仅取得占用但尚未通过用户加入确认的连接也会延长旧恢复凭据的期限。

## 具体修改

| 文件 | 关键符号 | 修改 |
| --- | --- | --- |
| [JvmListenTogetherService.kt](../../composeApp/src/jvmMain/kotlin/com/resonance/player/together/JvmListenTogetherService.kt) | 房主 `acceptPeer` 的 `finally` | 持有槽位直至当前代旧连接的引用和状态完成清理，再释放 `busy`；离房后的旧协程不再改写新一代房间的恢复期限 |
| 同上 | `established`、`resumeUntil` | 仅在已成功发送欢迎消息的连接断开时开启新的 30 秒恢复期限，未通过加入确认的尝试不延长旧凭据有效期 |
| 同上 | `nextResumeKey`、世代锁 | 创建新恢复凭据后，仅在同一世代仍有效时与连接引用一起写入；欢迎消息使用该次握手的局部令牌，避免退出后旧协程覆盖新房间凭据 |
| 同上 | `issuedResumeKey` | 欢迎消息发送未完成时撤销该次已生成的令牌，避免部分写入后令牌保持无限恢复期限 |
| 同上 | `hostPeer` 的 `bye` | 撤销恢复凭据时核对连接和房间世代，避免过期连接的迟到退出包清除新连接凭据 |
| 同上 | `completeGuestHandshake` | 朋友端写入协商能力、恢复令牌和连接引用时同时核验世代与当前 socket，避免关闭后的旧握手改写新房间 |
| 同上 | `connectRacedGuest` | 多地址全部失败时优先保留 TLS 错误，避免普通连接失败掩盖证书问题而触发中继回退 |

## 修改前后行为

| 场景 | 修改前 | 修改后（按源码设计，尚未运行验证） |
| --- | --- | --- |
| 旧连接断开与新连接几乎同时到达 | 可能先接纳新连接再由旧收尾覆盖状态 | 先完成旧状态收尾，再开放占用槽位 |
| 未获同意的加入尝试结束 | 可能延长已有恢复令牌的期限 | 不延长已有期限 |
| 旧房间关闭时握手或收尾仍在运行 | 旧握手可能重写恢复凭据，旧收尾可能写入恢复期限 | 凭据写入和状态收尾都受世代检查保护 |

## 平台与数据影响

两端使用同一实现；不改变邀请格式、持久化数据、文件、权限或网络服务部署。当前仍是双人房间，该修复不能解决多人连接或证明跨网已经成功。
