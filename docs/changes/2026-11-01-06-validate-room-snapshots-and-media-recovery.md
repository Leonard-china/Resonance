# 2026-11-01 — 校验群快照修订号并修复贡献传输失败状态

- 修改日期：2026-11-01（Asia/Shanghai）
- 类型：房间协议与恢复修复；版本 0.6.5 / 39，未升版
- 影响平台：Android、Windows 共用房间协议
- 关联：[原生队列](2026-11-01-05-native-host-controls-and-playable-queue.md)、[群聊回执](2026-11-01-04-persist-group-chat-recipient-receipts.md)

## 需求或问题

并发快照可能先收到较新版本，再被旧版本覆盖；群快照未验证成员/队列数量、身份、文本和当前曲一致性。旧曲目迟到的 ready 会把新曲目标成已就绪，贡献上传失败没有清理待传输条目。

## 原因与依据

`guestPeer.groupSnapshot` 不检查 revision，`ready` 忽略媒体 ID，主端缺少 `mediaError` 分支，客端贡献源映射主要等离房才释放。部分文件还被误判为已有可播放缓存。

## 具体修改

| 文件 | 关键符号 | 修改 |

| [JvmListenTogetherService.kt](../../composeApp/src/jvmMain/kotlin/com/resonance/player/together/JvmListenTogetherService.kt) | 握手、群快照 | 实验群协议协商 `groupVersion=2`/`chatReceipts=1`；快照附房间 ID，只接受递增修订；限制 8 成员/50 曲目、唯一 ID、文本长度/控制字符、唯一且匹配邀请的协调设备、当前曲字段一致性 |

| 同上/两端 Runtime | `publishNativePlayback` | 提交采样时房间 ID，在服务锁内校验，避免旧房间采样污染新会话 |

## 修改前后行为

接收贡献媒体时对照已接受队列中的标题、歌手、时长；完整校验后推进快照修订，使“传输中→可播放”不会被同修订去重忽略。缓存命中只认已登记的可读曲目，不把 `.part` 当完成文件。删除当前曲后尚未到达原生播放器的旧采样，也不撤销既定替代曲选择。

按源码设计，旧快照不会撤销新队列；非法快照进入既有错误清理路径，不局部接受。失败且未缓存的贡献不再永久显示待传输。网络不可达仍可能连接失败，没有新建公共服务或假映射。

## 平台与数据影响

多人音频版本与聊天存储能力独立：有聊天存储时才声明 `chatReceipts=1`，无聊天存储的音频夹具不被误当成可回执的聊天参与者。群聊应按实际能力验收，不拿无存储夹具证明聊天。

仅修改内存和实验群协议；没有用户音频删除、凭据读取或升版。多人要求双方更新到当前协议，旧单对端另行处理，未承诺全量兼容。重连重置连接快照水位，接受一次完整状态再拒绝倒退。

输入校验/TLS 不替代成员签名，协调设备仍是群状态/内容的信任方；不宣称它无法伪造成员消息。端口/NAT/中继运行、慢成员公平性及服务存活需验收；协调设备迁移另需协议设计。
