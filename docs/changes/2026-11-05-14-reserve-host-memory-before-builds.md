# 2026-11-05 — 按用户要求停止内存紧张构建并预留桌面内存

- 修改日期：2026-11-05（Asia/Shanghai）
- 类型：构建验证流程／文档
- 版本：0.6.6 / 40，不升版
- 平台：当前共享 Linux 桌面
- 需求：用户明确要求“不要让我的内存爆满”；延续[资源预算](2026-11-05-05-limit-local-build-memory.md)。

## 需求或问题

仅限制构建进程树上限仍不足以保护已被用户应用占用的桌面。前轮完整编译在总可用内存很低时运行；用户提出要求后立即停止当前验证，不继续启动重型 APK 打包。

## 原因与依据

进程树限额只能限制本项构建，不代表宿主机有同等空闲容量。需要同时检查 `/proc/meminfo` 的 `MemAvailable`，并为用户应用留出余量。构建串行锁也要跨当前两个对话共享。

## 具体修改

| 文件或入口 | 关键项 | 修改 |
| --- | --- | --- |
| [AI-WORKFLOW.md](../AI-WORKFLOW.md#本机资源预算) | 本机资源预算 | 启动前可用内存至少为实际进程树硬上限加 1536 MiB；低于门槛排队或记录受阻。运行中可用内存低于 1536 MiB，停止本构建。 |
| 本轮忽略目录 `build/assistant-cost-and-lyrics-drag-2026-11-05/when_build_idle.py` | 共享 flock、cgroup memory.max、余量监测 | 从实际 cgroup 读取硬上限，不只依赖环境变量；共享 `build/resonance-heavy-validation.lock`；只停止自己的进程组／专用服务，不关闭用户应用。 |

默认 2 GiB 上限对应 3.5 GiB 启动门槛。本轮重型包使用 1.5 GiB 上限，至少需要 3 GiB 可用；轻量原生检查使用 512 MiB 上限，需要 2 GiB 可用；单独桌面打包尝试使用 768 MiB 上限，需要 2.25 GiB 可用。均禁用本构建的 swap，不修改系统 swap、全局 Gradle 或用户应用。

## 修改前后行为

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 宿主机只剩约 1 GiB 可用 | 仍可能启动有 1.5 GiB 硬上限的编译 | 不满足“上限＋余量”，不启动 |
| 两个对话同时验证 | 独立检查可能竞态 | 共用构建锁并检查残留 Java 构建 |
| 运行中用户应用增加占用 | 构建继续到自身硬上限 | 可用内存不足时中止自身构建 |

## 平台与数据影响

不改播放器业务、用户音乐、设置、凭据、版本或发布产物格式。已编译代码和先前安装保留；新 APK 尚未打包／安装，不能把前次安装算作本轮交付。

## 验证

- 已停止 `resonance-cost-drag-final-validation-20261105-r2`，确认 inactive，无残留编译器／Gradle／测试 JVM；停止后宿主机可用内存约 2.3 GiB。
- 最终完整源码：桌面 200 份编译通过，之后仅按完整模块元数据保留方式增量重编译 Android JSON 兼容修正的类；Android 191 份完整编译通过；69 项最终回归全部通过。
- 新门槛下轻量原生检查：512 MiB 硬上限／384 MiB 软上限／Swap0，峰值 285.2 MiB；两倍缩放三项通过，旧实现对照三项中新增用例预期失败一项。
- 单独桌面打包：768 MiB 硬上限，启动须至少 2304 MiB 可用。观察期内门槛未持续满足，等待 60 秒后退出，Gradle 没有启动；确认启动保护实际生效。未故意耗尽真实内存来测试运行中中止。

## 限制与后续

其余应用的内存占用不由本构建控制。门槛不足时保留产物并明确报告受阻，不自动提高预算或关闭用户程序。手机完整包待可用内存满足 3 GiB 后再继续。
